# Phase 7: natural-language search walkthrough

## 7.1 CLIP image encoder ([clip.cpp](../../engine/src/embed/clip.cpp))

- Model: CLIP ViT-B/32 image tower with its projection, exported to ONNX by `Xenova/clip-vit-base-patch32` (input `pixel_values[N,3,224,224]`, output `image_embeds[N,512]`).
- Preprocessing (`preprocess`): resize so the short side is 224 (bicubic), take a 224×224 square, BGR → RGB, scale to 0–1, subtract CLIP's mean `(0.48145466, 0.4578275, 0.40821073)` and divide by its std `(0.26862954, 0.26130258, 0.27577711)`, NCHW. The output is L2-normalised so a dot product is a cosine similarity.
- **Crops.** A 16:9 dashcam frame resized to a 224 short side is 398×224, so a centre crop throws away 44% of the width, including cars in the side lanes and roadside signs. `crops: "three"` embeds the left, centre and right squares in one batched call. Go stores the centre as model `clip-vit-b32` and the others as `clip-vit-b32/left` and `/right`, so both modes can be searched from the same data (search keeps the best crop per keyframe).
- Tests ([bpe_test.cpp](../../engine/tests/bpe_test.cpp)): the same image gives identical vectors with norm 1; on a frame of the city clip, "a car" scores the crop of an SUV above a crop of conifers; three-crop mode returns three vectors.

## 7.2 BPE tokenizer and text encoder ([bpe.cpp](../../engine/src/embed/bpe.cpp))

CLIP's tokenizer, re-implemented in C++ from `vocab.json` and `merges.txt`:

1. **Clean**: lowercase, collapse whitespace runs to one space, trim.
2. **Pre-tokenize** like CLIP's regex: `<|startoftext|>`, `<|endoftext|>`, the contractions `'s 't 're 've 'm 'll 'd`, runs of letters, single digits, runs of other non-space symbols. Letters cover ASCII, Latin-1/Extended, Greek, Cyrillic and CJK; queries here are English.
3. **Byte mapping**: each UTF-8 byte becomes a printable code point with GPT-2's reversible table (so the vocabulary never contains control bytes).
4. **BPE**: split a word into symbols, append `</w>` to the last, then repeatedly merge the adjacent pair with the lowest rank in `merges.txt` (all its occurrences, left to right) until no ranked pair is left. Look each piece up in the vocabulary.
5. Add start `49406` and end `49407`; cut to fit 77; `encode_padded` pads with the end token to 77 (the text model pools at the end token, so padding after it doesn't change the result).

The text tower (`clip_text.onnx`, `input_ids[1,77]` → `text_embeds[1,512]`) output is L2-normalised.

Golden test: [testdata/tokens/clip_golden.json](../../testdata/tokens/clip_golden.json) holds ids for the 20 strings in `queries.txt` (contractions, punctuation, digits, repeated spaces, upper case, `café`), produced once with the Hugging Face `tokenizers` library and `openai/clip-vit-base-patch32/tokenizer.json`. All 20 match exactly.

## 7.3 Protocol

`embed_frames {path, every_sec, crops}` streams one `embedding {t, crop, vector}` per keyframe and crop, then `done`; `embed_text {text}` returns one `embedding {vector}` and `done`. Vectors are 512 floats rounded to 6 decimals. CLIP sessions load on first use; `engine serve --lazy` also defers YOLOX so a search starts quickly. The fake engine answers both commands with deterministic unit vectors for Go tests.

## 7.4 Keyframe indexing

- Migration [0003_search.sql](../../go/internal/store/migrations/0003_search.sql) (0002 was taken by the clock offset in 1.7) adds `keyframes(id, job_id, segment_id, t_offset_s, model, vector BLOB)`, vectors as 512 little-endian float32 (2,048 bytes). `job_id` lets an interrupted job's rows be removed exactly like observations.
- `rearview process --embed [--camera front]` plans one `embed_frames` job per segment that has none (front at priority 0, others after) and runs them through the same pipeline; the writer stores each `embedding` reply. Re-running skips segments that already have a job.

## 7.5 Search ([search.go](../../go/internal/search/search.go))

1. Load every vector into memory (front footage: about 19,000 keyframes × 3 crops × 2 KB ≈ 115 MB; centre only ≈ 38 MB).
2. Embed `search.prompt_template` filled with the query ("a dashcam photo of {query}") with the engine.
3. Score every keyframe by dot product; with three crops a keyframe's score is its best crop.
4. Keep the `top_k` (50) best keyframes; group those in the same file within `group_s` (5 s) of each other into a **moment**, placed at its best keyframe; rank moments by their best score.
5. Print time, trip, score, camera, GPS position and file; `--clip` cuts a 10 s clip around each; `--json` prints the hits for the viewer.

Speed: 57,798 vectors (19,266 front keyframes × 3 crops) searched in 0.6–0.8 s including the CLIP text pass; engine start and index load add 0.2–0.5 s.

## 7.6 Evaluation

`rearview eval --search` reads [testdata/search_queries.csv](../../testdata/search_queries.csv) (query, local time range) and reports, for four variants, whether a moment overlapping the range is in the top 5.

The 24 queries were **drafted by the agent** from contact sheets (one frame every 15 s) of six recordings; each range is the sampled frame ± 5 s. They still need the owner's confirmation (input needed).

| Variant                      | Hood/overlay kept | Hood/overlay cropped (kept) |
| ---------------------------- | ----------------- | --------------------------- |
| Centre crop, prompt template | 5/24 (21%)        | 3/24 (12%)                  |
| Centre crop, plain query     | 4/24 (17%)        | 5/24 (21%)                  |
| Three crops, prompt template | 3/24 (12%)        | 3/24 (12%)                  |
| Three crops, plain query     | 2/24 (8%)         | 5/24 (21%)                  |

Far below the 70% target. What the misses show:

- **The test is stricter than the task.** Each query has a single labelled ±5 s range, but most queries ("white pickup truck", "stop sign at a suburban intersection", "red traffic lights at night") occur dozens of times in 5.35 hours. A top-5 hit on another real pickup counts as a miss. Spot checks: "a bus" returned travel trailers, "a cyclist" a pedestrian-crossing sign, so CLIP does find the right _kind_ of thing; there may simply be no bus or cyclist in this footage. A fair test needs either queries for unique moments or every occurrence labelled.
- **Wide frames hurt.** A 224×224 crop of a 16:9 frame loses most of the scene; distant objects (a 417 sign, a tower crane) are a few pixels after the downscale. Three crops help small side objects (tall tower 1st, red tree 5th) but add false matches.
- **The hood and the camera's text overlay** are in every frame; cropping them out (bottom 22%) helped the three-crop variants (8–12% → 12–21%) and left the best centre-crop score unchanged. It is kept.
- The prompt template ("a dashcam photo of …") helped before the crop and hurt after: with 24 queries a single query is 4 points, so the differences between variants are within noise.

Next steps, not done: label all occurrences for 10 rare queries; tile each frame into a 2×4 grid of crops instead of 3 squares; a larger CLIP (ViT-L/14).
