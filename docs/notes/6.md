# Phase 6: performance walkthrough

All numbers from `rearview bench` on the dev PC (Ryzen 7 7800X3D, RX 9070 XT, Windows 11), front camera, 2560×1440 H.264 at 30 fps, analysed at 10 fps with detection, tracking, distance and TTC. "Subset" = the first 5 files of [bench/set.txt](../../bench/set.txt) (15 min); "full set" = all 21 files (61.9 min: trip 2 day city and highway, plus 5 night files of trip 5). History: `rearview bench table`; raw runs in [bench/results/](../../bench/results/).

## 6.1 Benchmark command ([bench.go](../../go/internal/bench/bench.go))

- Copies the set's segment rows into a scratch database, plans one whole-file `analyze` job per file and runs the normal pipeline, so the benchmark measures exactly what `process` does.
- **Minutes per hour** = wall-clock minutes ÷ hours of footage.
- **Per-stage times** come from the engine: every `done` reply carries `stages_ms` (decode, preprocess, inference, post-process, tracking, geometry), summed over jobs and divided by frames. With the threaded engine these are per-thread CPU time, not wall time, so they can add up to more than the elapsed time.
- **Worker utilization** = time workers spent on jobs ÷ (workers × elapsed).
- **Peak memory**: the engine reports its own peak working set (`GetProcessMemoryInfo`) in `done` as `peak_mem_mb`; the max is kept.
- **GPU utilization**: a PowerShell `Get-Counter` loop samples Windows' `GPU Engine` counters (3D and compute engines, all processes) about once a second; the busiest engine type per sample is averaged. AMD's driver exposes these counters.
- Saved to `bench_runs` and `bench/results/<time>_<sha>.json`; `bench compare` prints the last two side by side, `bench table` prints the markdown history (task 6.8).
- Reproducibility: two full-set runs on the same commit gave 2.42 and 2.38 minutes per hour (1.7% apart, within the 5% target).

## 6.2 CPU baseline

| Configuration (subset)            | Minutes per hour | Frames/s |
| --------------------------------- | ---------------- | -------- |
| 1 worker × 8 ONNX Runtime threads | 30.3             | 18.6     |
| **2 workers × 4 threads**         | **28.0**         | **20.1** |

Inference is about 95% of the time (50 ms per frame for YOLOX-s at 640×640); decode with frame skipping is about 2 ms. Two workers win slightly: the per-frame work outside inference (decode, resize, tracking) overlaps with the other worker's inference.

## 6.3 GPU inference

- **DirectML** (`--device dml`, preset `dev-dml`): ONNX Runtime's DirectML build 1.24.4 (the last one; DirectML is in maintenance) plus `DirectML.dll`, both from NuGet with pinned SHA-256 in [onnxruntime.cmake](../../engine/cmake/onnxruntime.cmake). Inference drops from 53 ms to about 3 ms per frame. Detections on the city clip are **identical** to the CPU run (same boxes, confidences and track ids in all 199 frame lines). The "some nodes were not assigned" warning is ORT keeping shape ops on the CPU, which is expected.
- **MIGraphX through Windows ML** (`--device migraphx`): not done. It needs the Windows App SDK's Windows ML runtime, its own `onnxruntime.dll`, and the execution-provider catalogue API to download AMD's EP at run time; the stock ORT build answers `--device migraphx` with "not available". With DirectML already at 3 ms per frame, inference is no longer the bottleneck (see below), so MIGraphX could not change the headline by more than a few percent.

## 6.4 Hardware decoding ([ffmpeg_source.cpp](../../engine/src/decode/ffmpeg_source.cpp))

`FfmpegSource` implements the same `FrameSource` interface on libavformat/libavcodec, with D3D11VA (VAAPI on Linux) when `hardware` is set. Every frame is decoded (H.264 needs it); only sampled frames are copied from the GPU (`av_hwframe_transfer_data`) and converted to BGR with swscale.

- Same frames and timestamps as the OpenCV source on the test clip (test `SameFramesAsOpenCv`). The first hardware run differed by 6.5 grey levels on average: the VIOFO streams are full-range (`yuvj420p`), and NV12 frames from the GPU lose the "J", so swscale assumed limited range. The source now passes the range explicitly; the difference is under 4 levels (rounding).
- **Result: slower.** 6.4 minutes per hour versus 2.5 with OpenCV's software decoder (subset, DirectML, 2 workers). The CPU decoder uses frame threads across 16 hardware threads and skips the colour conversion for unsampled frames; the D3D11VA path decodes one frame at a time and pays a GPU→CPU copy of a 2560×1440 frame for every sample. Kept behind `--decoder ffmpeg` for machines with weaker CPUs; the default stays `opencv`.

## 6.5 Threaded pipeline inside the engine ([analyzer.cpp](../../engine/src/pipeline/analyzer.cpp))

Decode thread → bounded queue (4) → preprocess thread (letterbox + NCHW) → bounded queue (4) → inference, tracking, geometry and output on the calling thread. `Detector::prepare` touches no shared state, so it can run beside `infer`. Order is preserved, so results are identical to the serial loop (test `ThreadedMatchesSerial` compares the JSON byte for byte). Errors in a thread are captured as `exception_ptr` and rethrown after `join`; cancel closes both queues so no thread blocks.

Subset, DirectML, 2 workers: serial 3.05 → threaded 2.46 minutes per hour (−19%), GPU utilization 48% → 59%.

## 6.6 Batched inference

Not possible with the released YOLOX-s export: its input is fixed at `images[1,3,640,640]` (`engine info`). `Detector::infer` already batches when a model has a dynamic batch dimension and falls back to one frame per call otherwise. Re-exporting the model needs Python, which the repo avoids, and at 3 ms per frame inference is no longer where the time goes.

## 6.7 Smarter scheduling

- **Lower rate on empty stretches**: `analyze` accepts `idle_fps` / `idle_after`; after 20 frames with no detection the engine drops to `idle_fps` and returns to full rate on the next detection (`set_sample_fps` on the frame source; TTC uses the real time between frames). Test: 10 s with nothing detected costs about 30 frames instead of 100.
- **Measured: no gain** (2.47 vs 2.46 minutes per hour at `idle_fps` 5). With DirectML the bottleneck is decoding all 30 frames per second of 1440p H.264 (8 ms of decode and 6 ms of resize per analysed frame, against 3 ms of inference), and skipping inference doesn't skip decoding. Kept off by default; Phase 5 accuracy is unaffected.
- **Workers**: 1 → 2 workers is −14%; 3 workers is no better than 2 (2.49), as the CPU decoders saturate. Default `engine.workers: 2`.
- Parking footage is never planned (task 4.4).

## Where the time goes now

Per analysed frame on the full set: decode 8.3 ms, preprocess 6.2 ms (resizing 2560×1440 to 640), inference 6.4 ms, everything else under 0.2 ms, spread over 2 workers and 3 threads each. The next step would be resizing on the GPU, or decoding at reduced resolution.
